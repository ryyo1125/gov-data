このセッションでやったことを `.claude/diary/` に記録する。
次のセッションが `/activate` でこれを読んで再開する。

## 前提

**このリポジトリのコンテナは毎回作り直される。コミットしていないものは失われる。**
diary もリポジトリの一部なので、書いたら必ずコミットして push する。
push まで終えて初めて引き継ぎが成立する。

## 手順

1. 実測して事実を集める。記憶や印象で書かない。

   ```bash
   date -u +%Y-%m-%dT%H:%M:%SZ
   git rev-parse --short HEAD
   git branch --show-current
   git log --oneline -10
   git status --short
   ```

2. `.claude/diary/<YYYY-MM-DD-HHMM>.md` を書く（UTC。`date -u +%Y-%m-%d-%H%M`）。
   下のテンプレートに従う。

3. 台帳まわりを触っていたなら、記録の前に状態を確定させる。

   ```bash
   .work/toolvenv/bin/python registry/build.py --check
   ```

4. diary をコミットして push する。

## テンプレート

```markdown
---
date: <UTC ISO8601>
commit: <記録時点の HEAD（短縮）>
branch: <ブランチ名>
---

# <YYYY-MM-DD> セッション記録

## やったこと

<何を、なぜ。コミット単位ではなく意図単位で 3〜6 項目。
 コミットの一覧は git log で読めるので、ここには「なぜそうしたか」を書く>

## いまの状態

<ブランチ、未コミットの有無、検証・ビルドの通過状況。
 壊れている箇所があれば隠さず書く>

## 次にやること

<次のセッションが最初に着手すべきこと。優先順に。
 「〜を検討」ではなく、着手できる粒度で書く>

## 判断とその理由

<後から「なぜこうなっているのか」と思われそうな選択と、その理由。
 これが無いと次のセッションが同じ議論を最初からやり直す>

## 未解決・保留

<解決していないこと、意図的に見送ったこと、ユーザーの判断待ち。
 「無い」なら「無い」と書く。空欄にしない>
```

## 書くときの原則

- **実行して確かめたことだけ書く。** 「通ったはず」を「通った」と書かない
- **失敗や未完了を隠さない。** 引き継ぎの価値は、うまくいかなかったことの方に
  ある。次のセッションが同じ壁に無駄な時間を使わずに済む
- **長くしない。** 次のセッションが読む前提なので、読み切れない引き継ぎは
  読まれない。git log で分かることを転記しない
- **ユーザーの判断待ちがあれば必ず「未解決・保留」に書く。** これを落とすと、
  次のセッションが勝手に決めてしまう
