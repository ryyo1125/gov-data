# 情報源台帳へのエントリ追加

## この台帳が守ろうとしていること

データ源の一覧は、作った瞬間から腐り始める。政府 API は予告なく仕様が変わり、
ドキュメントは実装より古く、そして最悪なのは**腐ったことに誰も気づけない**ことだ。

だからこの台帳は、エントリと「再実行可能な検証スクリプト」を必ず対にする。
台帳の価値は網羅性ではなく、**実際に叩いて動いた記録**にある。
`data.go.jp` のようなカタログは既に存在するので、その劣化コピーを作っても意味がない。

この前提から、3 つの規律が出てくる。

1. **検証ステータスは手で書けない。** `registry/sources/*.yaml` に書けるのは事実と、
   検証を再現するためのポインタだけ。合否・検証日は `registry/build.py` が
   `results/` の実行結果から導出する。`status:` を手書きするとビルドが落ちる。
2. **主張には根拠が要る。** `findings` は `claim` と `evidence` の組でしか書けない。
   「たぶんこうだろう」を書く場所は無い。
3. **「なし」と「不明」を混ぜない。** 一次資料に記述がなければ `undocumented`。
   これを「なし」や空欄にすると、推測が事実の顔をして台帳に入り込む。

## 進め方

### 1. 対象を 1 つに絞る

粒度は**提供元ではなく 1 エンドポイント（または 1 MCP サーバー）**。
e-Stat のような API 群を 1 エントリにまとめると、認証も到達性も安定性も
まとめて嘘になる。まず何を検証するのか 1 つに決める。

網羅を目指さないこと。使う予定のあるものだけを深く検証する。

### 2. 先に到達性を確かめる

一次資料を読み始める前に、対象ホストへ到達できるかを確認する。順序が逆だと、
仕様を調べ切ってから「そもそも繋がらない」と分かって全部が無駄になる。

```bash
.work/toolvenv/bin/python verify/verify_reachability.py --out results/reachability.json
```

`.work/toolvenv` は `./verify/run_all.sh` が作る。無ければ先に一度回すこと。
システムの `python` には httpx も PyYAML も入っていないので動かない。

新しいホストは `registry/candidates.yaml` の `candidates:` に足してから回すと、そのホストも実測される。

**到達できない場合、そこで止まる。** 二次情報（Web 検索結果や解説記事）だけを根拠に
エントリを書いてはいけない。それは推測を台帳に入れる行為で、この台帳が防ごうとしている
ことそのものだ。代わりに `registry/candidates.yaml` に候補として記録する。

```yaml
  - id: jma-xml
    name: 気象庁防災情報XML（PULL型 Atom フィード）
    why: なぜ調べたか
    hosts: [xml.kishou.go.jp, www.jma.go.jp]
    blocker: unreachable       # unreachable / credentials / not_started
    blocker_detail: 何がどう到達できなかったか（プロキシ 403 なのか先方の障害なのか）
    next_step: 何が解消すれば検証に進めるか
```

`blocker` は「**なぜまだ検証していないか**」であって、その情報源の性質ではない。
環境が変われば古くなるので、`build.py` が到達性の実測と突き合わせ、
`unreachable` と書いてあるのに到達できる候補には「記録が古い」と表示する。

**候補にはその情報源が何を提供するかを書かない。** 一次資料に当たる前に書けるのは
名前とホストと調べた理由だけで、それ以外は推測になる。認証情報が無くて実行できない
ものは `credentials`、到達できて着手していないだけなら `not_started`。

### 3. 一次資料を読む

OpenAPI 仕様やソースコードのような**機械可読な一次資料**を最優先で探す。
人間向けのドキュメントページより信頼できるし、記述の「不在」も確認できる。

- OpenAPI/Swagger: `/swagger-ui/`、`/openapi.json`、`/v3/api-docs` を試す。
  Swagger UI が JS で動くページなら `swagger-initializer.js` に仕様の URL が書いてある
- MCP サーバー: リポジトリを clone してツール定義のソースを読む。
  README に書かれていない引数や制約がそこにある
- 探すもの: エンドポイント一覧、`securitySchemes`（無ければ認証不要の強い根拠）、
  レート制限、利用規約、安定性・試行版に関する記述

**利用規約は API のドキュメントに無いことが多い。** 提供元ポータルのフッター
（`/terms`、`/service-policy` など）を必ず見る。法令 API の規約は API 側ではなく
e-Gov ポータルにあり、しかも適用範囲が「e-gov.go.jp 及びそのサブドメイン」と
書かれていた。ホスト名が違うから無関係とは限らない。

ここで**見つからなかったこと**も成果である。`undocumented` として記録する。

### 4. 検証スクリプトを書いて実行する

`verify/verify_<id>.py` を作り、`verify/_report.py` の `Reporter` を使う。
全検証が同じ形の JSON を出すことで、`build.py` が結果を機械的に読める。

`results/` には性質の違う 3 種類が入る。混同しないこと。

- `results/<エントリ id>.json` — エントリ 1 件の検証結果。台帳の status の根拠になる
- `results/reachability.json` — ホストの到達性。自環境の状態であって提供側の状態ではない
- `results/fields.json` — 取得できる項目の抽出結果。検証ではないので status には効かない

```python
reporter = Reporter(SOURCE_ID, target)
await reporter.step("GET /laws", _get_json(client, "/laws", {"limit": 3}))
reporter.skip("GET /attachment/{id}", "添付を持つ法令が見つからなかった")
reporter.write(out_path)
```

書くときの勘所:

- **公開されている機能はすべて叩く。** 1 つでも未実行なら台帳は不完全になる
- **前提が揃わず実行できなかったものは `skip`。** 成功と失敗のどちらでもない状態を
  潰さないこと。「添付ファイルを持つ補助金が少ない」ような事実がここから見つかる
- **入力は固定するが、変わる ID はハードコードしない。** 例えば法令の
  `law_revision_id` は改正のたびに変わるので、都度引き直す。ハードコードすると
  数か月後に「仕様変更」と誤診する
- **レスポンス全体は保存しない。** 件数と骨格だけを残す（`_digest` 相当）。
  巨大な JSON をコミットしても誰も読まない
- **プロキシ環境を尊重する。** httpx なら `trust_env=True`。CA や
  `HTTPS_PROXY` を無効化して通そうとしない

MCP サーバーが対象なら、clone から起動・検証までを通しで行うランナーも用意する
（`verify/run_jgrants_verification.sh` が手本）。クリーンな状態から再現できることを
必ず確かめる。そこまでやって初めて「確実な手順の記録」になる。

### 5. 到達不能の原因を切り分ける

到達できないとき、**「存在しない」と書いてはいけない**。原因は 3 つに分かれ、
書き先も変わる。ここを混同すると「先方が塞いだ」と誤診して台帳が嘘になる。

| 症状 | 意味 | 書き先 |
|---|---|---|
| プロキシから 403/407（httpx なら `ProxyError`、curl なら CONNECT tunnel failed） | 自環境の egress ポリシー | 一部なら `reachability.hosts` の `note`。全部塞がれていて検証できないなら `candidates.yaml`（`blocker: unreachable`） |
| 先方から 4xx/5xx（`status_code` が取れている） | 先方の仕様・障害 | エラーコードごと `findings` に記録 |
| 特定のツールだけ失敗し、別のツールでは通る | ツールごとに egress の経路が違う | ツール名まで含めて `findings` に記録 |
| 既定の User-Agent で 403、ブラウザ相当の UA で 200 | 先方の WAF | `findings` に記録。egress のせいにしない |
| 名前解決失敗・タイムアウト | サービス終了の可能性 | 一次資料で確認してから書く |

`ProxyError` と先方の 403 は見た目が似ているが意味が正反対なので、検証スクリプトでも
必ず分けて扱う（`Reporter.blocked()` が前者用）。

**1 つのツールで駄目でも、そこで諦めない。** WebFetch が塞がれていても Bash の
curl や httpx では通ることがある（実際に xml.kishou.go.jp と www.e-gov.go.jp が
そうだった）。403 が返ったら UA を変えて試す。これらは推測で片付けず、
どのツールで何が返ったかを実測して記録する。

窓口 URL と実 API ホストが違うことがよくある（`www.data.go.jp` の CKAN API は
`data.e-gov.go.jp` へリダイレクトされる）。`reachability.hosts` には
**実際に通信が発生するホストをすべて**、役割付きで列挙する。

### 6. エントリを書く

`registry/sources/<id>.yaml`。スキーマは `registry/schema.json`、
手本は既存の `jgrants-mcp.yaml` と `egov-hourei-api.yaml`。

判断が要るところだけ補足する。

- **`data_source.authority` と `access` は独立に評価する。** データの権威性と
  経路の信頼性は別物。一次公開元自身のラッパー実装でも、その実装が実験版 API を
  叩いていることはある。「公式だから安心」と丸めないためにこの 2 軸がある
  - `primary_official`: 一次公開元が直接提供
  - `official_wrapper`: 一次公開元自身によるラッパー実装
  - `third_party_wrapper`: 第三者によるラッパー
  - `unknown`: 提供主体を確認できなかった場合。分からないことを分かると書かないための逃げ道
- **`requirements.auth` に `not_required` と書けるのは、認証情報なしで実際に
  応答したときだけ。** 仕様に記述が無いだけなら `undocumented`。
  両方に該当するなら `not_required` にして `auth_note` に事情を書く
- **認証情報そのものは絶対に書かない。** `credential_env` に環境変数名だけを書く
- **`usage_restrictions` には法的・契約的な制約を書く。** 出典表示だけが制約とは
  限らない。気象庁の電文は「予報の値を編集する行為は気象業務法第 17 条の許可が
  必要」で、これを知らずに加工すると違法になる。確認していないなら、その旨を
  要素として書く（空配列は「制約が無いことを確認した」の意味になる）
- **件数などの実測値は `content.coverage` ではなく `content.measured` に書く。**
  coverage は質的な説明、measured は「検証スクリプトが実際に取得した数値」。
  ビルドが measured の数値を results と突き合わせるので、取得していない数値を
  書くと落ちる。
- **`measured` に載せてよいのは、変化したら気づく価値がある数値だけ。**
  この検査はドリフト検知器なので、変動が速い数値を載せると毎回落ちるだけの
  ノイズになり、本当に意味のある変化が埋もれる。目安は次のとおり。
  - 載せる: 法令の総数、カタログのデータセット数（年単位で緩やかに増える）
  - 載せない: 募集中の補助金数（日々変わる）、フィードの entry 数（毎分変わる）
  載せないと決めたら `measured: []` と明示し、coverage に「なぜ書かないか」を書く。
  空配列は「実測値を載せないと判断した」という意思表示になる
- **`stability.notes` には一次資料に明記された記述だけ。** URL の見た目からの
  推測（`/exp/` が実験版を意味する等）は、事実として `notes` に書かず、
  「パスに exp を含む」という観察事実だけを書く

### 7. `findings` を書く

ここが台帳の中身で最も価値がある。**実行して初めて分かったこと**を書く。
ドキュメントを読めば分かることは書かなくていい。

良い `findings` は、次に同じ API を触る人が踏むはずだった地雷を消す。

```yaml
findings:
  - claim: 添付ファイルが存在しない ID を /attachment に渡すと、404 ではなく HTTP 400 で code 404003 が返る。
    evidence: 321CONSTITUTION_19470503_000000000000000 を指定して {"code":"404003",...} を確認。
  - claim: 公式ドキュメントには認証要否・レート制限・利用規約の記述が無い。
    evidence: https://developers.digital.go.jp/documents/jgrants/api/ を参照して該当記述が無いことを確認。
```

`evidence` には「どの実行結果の・どのステップで・何を見たか」を書く。
「実行して確認した」だけでは、後から検証できないので根拠にならない。

### 8. ビルドして確認する

```bash
.work/toolvenv/bin/python registry/build.py
```

（`.work/toolvenv` は `./verify/run_all.sh` が作る。無ければ先にそれを一度回す。）

ここで落ちるのは次の場合。落ちたら直す。**通らないまま「登録した」と報告しない。**

- スキーマ違反（型・必須項目・列挙値）
- `id` とファイル名の不一致
- `verify.script` が存在しない、または `verify/run_all.sh` から実行されない
- 結果ファイルがあるのに `source_id` がエントリ id と一致しない
- `content.measured` に書いた数値が、対応する検証結果に見当たらない

一方、**結果ファイルがまだ無いのは落ちない**。未検証は正当な状態なので、
`unverified` として台帳に出るだけになる。「ビルドが通った」＝「検証済み」ではないので、
ビルドの出力で各エントリの状態を必ず確認すること。

`--check` は生成物が最新かだけを見る。CI や定期実行で使う。

台帳の規律はすべてこの検査に依存しているので、検査自体にも回帰テストがある。
`build.py` の判定を変えたら `bash registry/test_build.sh` を回すこと。
上に並べた「落ちる／落ちない」の条件は、そこで実際に壊して確かめている。

**新しい検証スクリプトは `verify/run_all.sh` にも足す。** これを忘れると、
そのエントリだけ定期再検証から漏れて黙って腐る。忘れてもビルドが落ちるようにしてあるが、
落ちてから直すのではなく最初から足しておくこと。MCP サーバーのように起動が要るものは、
`run_jgrants_verification.sh` のようにラッパー経由で呼んでよい。

新しい情報源を足したら `verify/extract_fields.py` にも抽出処理を足す。台帳は
「どこから何が取れるか」をエンドポイント粒度で答えるが、それだけでは
「取ってきた結果にどの項目が入っているか」に答えられない。抽出では、
提供側が定義した仕様（OpenAPI の schema、MCP のツール定義）と、実データを読んで
列挙したものを必ず区別して `origin` に記録する。後者はサンプルに現れなかった項目が
落ちるため、網羅を保証できないことを利用者に伝える必要がある。

## やってはいけないこと

- 実行していない手順を書く。動くはずの手順ではなく、動いた手順だけを書く
- 一次資料に無い数値や制約を、経験や一般論から補う
- 一次資料に到達できないまま、Web 検索や解説記事の内容でエントリを埋める
- 検証が一部失敗しているのに、その事実を台帳から隠す。
  `failed` も立派なステータスで、`build.py` がそう表示する
- 到達できなかったことを「提供終了」と解釈する
- 台帳を網羅的にしようとして、検証していないエントリを大量に足す

## 既存エントリの再検証

仕様変更を検知するために、定期的に `./verify/run_all.sh` を回す。
`results/` に差分が出たら、それは提供側が変わったということ。
ただし `results/reachability.json` の差分だけは自環境側の変化なので、
提供側の仕様変更と取り違えない。
差分を読んで、`findings` と `stability.notes` を更新する。

最終検証から 90 日を過ぎたエントリは `build.py` が `stale`（要再検証）にする。
