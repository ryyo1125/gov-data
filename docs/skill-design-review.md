# 「情報源台帳スキル」構想レビュー

構想: 信頼できるデータ提供源を探索し、提供元・提供方式・情報の種類と形式・頻度・接続方法を
推測なしで台帳化する — これをスキル化する。

## 総評

**方向は正しい。ただし今の形のままスキルにすると、目的（推測の排除）が壊れる。**
理由は下記3点。改善すれば、むしろスキル化の価値が高い類の仕事である。

## 問題1: 異質な2つの仕事が同居している

| | 探索(discover) | 記録(record/verify) |
|---|---|---|
| 性質 | 発散的・判断依存 | 収束的・スキーマ拘束 |
| 頻度 | ソースごとに事実上1回 | 反復・定期 |
| 成功条件 | 網羅性 | **証拠の厳密さ** |

同居させると、探索の勢いで「たぶんこうだろう」が台帳に流れ込む。
**最も避けたいことが、この同居によって起きる。**

**改善:** 1スキル・2モードにし、**書き込み先ファイルを物理的に分ける**。
- `discover` モード → `candidates.csv` にのみ書く。接続方法の欄を**持たせない**
- `verify` モード → 1ソースを実際に叩き、成功したときだけ `sources.csv` へ昇格

## 問題2: 「確実な手順」はドキュメントからは作れない

公式ドキュメント通りに書いた手順は、実行するまで**仮説**である。
本プロジェクトで実証済み: Jグランツ公式MCPは手順通りに起動し `tools/list` まで通ったが、
API呼び出しは 403。しかもその403は**API側ではなく実行環境側**の egress ポリシーだった。

**改善:** `evidence_level`（E0〜E4）を必須列にし、
**`connection_procedure` は E3（実行確認）以上でなければ書かせない**。
さらに `verified_env`（実行環境ID）を必須にする。
**「動かなかった」はデータ源の属性ではなく環境の属性でありうる。**
環境を書かない失敗記録は、後から読むと嘘になる。

## 問題3: スコープが無限で停止条件がない

「信頼性の高いデータ提供サービス」は際限がない。停止条件のないスキルは
実行のたびに長さも品質も変わり、運用に乗らない。

**改善:** 起動時に必ず `scope`（対象領域）と `budget`（1回で verify する上限件数）を引数で取る。
探索は**公式登録簿を起点にする**と発散が止まる →
[e-Gov APIカタログ](https://api-catalog.e-gov.go.jp/info/ja/apicatalog/list) が政府APIの公式登録簿。
Web検索から始めるより網羅性・信頼性・停止性のすべてで優る。

## その他の改善点

4. **粒度を2層に。** 「提供元」1行では粗すぎる（e-Statは提供元1件でデータセット22万件規模）。
   `providers` と `sources`（エンドポイント/データセット単位）に分ける。→ 実装済み

5. **「頻度」は2種類。** データの更新頻度と、**提供方式の変更（仕様変更・廃止）の告知先**。
   後者が無いと台帳は黙って腐る。

6. **再検証を組み込む。** `last_verified_at` + `reverify_after`。
   台帳は資産ではなく生鮮品。スキルが真に価値を出すのは初回作成より**再検証の反復**。

7. **「信頼性」を隠れフィルタにしない。** 「信頼性が高いものだけ載せる」と基準が暗黙になる。
   基準を列にして記録し（提供主体の種別・一次情報か再配布か・ライセンス・出典表記義務・継続性）、
   **判断は読み手に渡す。** 再配布サービス（民間DB等）は排除せず、一次情報へのポインタ付きで載せる。

8. **利用条件を空欄禁止に。** 政府データは出典明記が義務のものが多い（Jグランツもそう）。
   `license` / `attribution_required` を `UNKNOWN` で埋めることは許すが、空欄は許さない。

## スキル化のタイミングについて

**今すぐスキルにするのは早い。** スキルは「反復して型が固まった手順」を凝縮するもので、
現時点で E3 まで通したソースは1件（Jグランツ）しかない。
1件から抽出した型は、ほぼ確実に間違った型を固定する。

**推奨: 手で3〜5件を verify してからスキル化する。**
特に提供方式が異なるものを選ぶ — REST API（要APIキー）／一括ファイルDL／
Webページからの取得。この3系統は接続手順の形がまったく違うため、
1系統だけで作った型は他に効かない。
その過程で `scripts/` に溜まった検証コードを、スキルが呼ぶ形にするのが最終形。
